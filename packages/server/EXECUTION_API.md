# Wallet execution protocol

The server never signs or broadcasts. Pricing remains read-only. Execution requires a configured trusted engine, reviewed pins and durable store. Local recipes reconstruct the Base ETH → Base USDC swap and pinned Base/Solana Relay deposits. An additional explicit `executionPins.providerManaged.enabled: true` mode enables official Relay transaction steps across configured EVM chains and Solana, including same-chain swaps, cross-chain ERC20 outputs, custom contract/mint addresses and source DEX composition. Chain/deployment metadata is discovered separately from quotes. This mode trusts Relay transaction construction and payout association; it still binds wallets/assets/amount/minimum/expiry/fees, simulates the exact source action and verifies canonical destination credit. Standard ERC20, classic SPL and supported passive Token-2022 extensions are admitted. Liquidity, usable RPC evidence, gas and supported token behavior remain necessary; other wallet VM families are not implemented. Price discovery alone never grants execution.

`execution.supportedRoutes` lists exact local pairs. Local profiles use `sourceChainId`/`destinationChainId`; the compact provider-managed profile uses `sourceChainIds`/`destinationChainIds` and `verification: "PROVIDER_MANAGED"`. Both bind asset classes and require `requiresFreshValidation: true`. The widget checks both chain arrays, supports custom addresses and attempts fresh preparation instead of enforcing a preset pair whitelist. Only the returned immutable review authorizes its exact claimed action.

Preparation that exceeds the requested economics returns HTTP 409 with `EXECUTION_FEE_LIMIT`, `EXECUTION_PRICE_IMPACT_LIMIT`, or `EXECUTION_FEE_AND_IMPACT_LIMIT`. The message includes the checked estimate and requested limit for both measures. Total fee estimates include the conservative source gas reserve, so they can exceed the provider's pricing preview. Only validated numeric fields are exposed; raw provider errors remain redacted. No execution is created and no limit is raised by these responses.

All calls use existing app authentication. Browser calls require the exact allowed Origin plus X-Router-App-Key. Server credentials are never accepted with Origin. App credentials identify the app, not a wallet owner.

## Wallet control

POST `/v1/wallets/challenge` accepts exactly `{chainId,address}` and returns `{challengeId,message,expiresAtMs,wallet}` plus the normal API envelope. Challenges expire after five minutes. EVM wallets sign the exact UTF8 message with personal_sign/EIP191. Solana wallets sign the exact UTF8 bytes using Ed25519, returning a base58 signature. Native token sentinel addresses are rejected as wallets.

POST `/v1/wallets/verify` accepts exactly `{challengeId,signature}` and returns `{walletToken,expiresAtMs,wallet}`. Nonces are single-use, including failed signatures. Tokens last fifteen minutes, are random 32-byte base64url values, and are bound to app, exact Origin (or server mode), chain and wallet. They do not grant signing authority. Proofs are memory-only; restart requires proving wallet control again, while executions remain durable.

Execution calls additionally require `X-Router-Wallet-Token`. Both app and wallet proof must match. CORS preflights allow this header only on known app origins. No cookies are used.

## Lifecycle

POST `/v1/executions/prepare` accepts the exact QuoteInput plus mandatory `nativeFeeBudgets:[{chainId,maxAmountRaw}]`. Budget amounts are positive raw decimal strings or explicit null for a fresh finite automatic reserve. The engine prepares fresh fixed terms; pricing snapshots cannot silently become execution plans (`EXECUTION_SNAPSHOT_UNSUPPORTED`). The response contains `{execution}`. Execution records are immutable in request, review hash and plan. Initial status is READY. Public plans show exact asset/sender/recipient/input/minimum/output expiry/native costs, and actions `{id,chainId,payloadHash}` without unsigned payloads. `payloadHash` is SHA256 over recursively key-sorted canonical JSON.

GET `/v1/executions/active` returns `{execution: record|null}` for the authenticated source wallet and app. Use it to recover a lost preparation response. GET `/v1/executions/:id` retrieves an owned record. Neverclaimed expired READY plans become EXPIRED and release the reservation.

POST `/v1/executions/:id/claim` accepts exactly `{reviewHash,revision}`. The host checks fresh independent chain evidence against unchanged saved terms, commits CLAIMED durably, then returns `{execution,action}`. Before asking the wallet to sign, a client must compare the action ID, chain and canonical payload digest to the approved review. Concurrent claims return at most one action. The client should durably remember execution ID and approved terms before requesting a claim, and record CLAIM_PENDING before that request. If the claim response is lost, retrieve the record; a CLAIMED record must never be signed again automatically.

POST `/v1/executions/:id/submit` accepts exactly `{transactionHash}` from the user's wallet result. A hash is a report, not proof of success. The journal rejects funding-hash reuse globally per chain across retained execution history, and rejects provider-order and destination-delivery replay. The same previously recorded hash is idempotent; a replacement hash is rejected.

POST `/v1/executions/:id/uncertain` accepts `{}` and records RECOVERY_REQUIRED after a claimed action with unknown signing/broadcast outcome. The wallet remains reserved; expiry does not authorize another action. A later original hash can be submitted for recovery.

POST `/v1/executions/:id/refresh` accepts `{}` and independently verifies the stored original hash. Pending receipts return `receiptStatus:PENDING` and preserve SUBMITTED. Verified successful destination credit satisfying exact asset, recipient and minimum permits COMPLETE (`receiptStatus:CONFIRMED`). An independently proven canonical reverted transaction returns `receiptStatus:FAILED` and terminal FAILED; ambiguous unsuccessful verification remains RECOVERY_REQUIRED. Provider status alone is insufficient.

Refresh is idempotent for terminal or already advanced records. Clients with a durably reported submission may call it directly without a preceding GET. Unknown or unreported wallet outcomes retain the original recovery flow. Refresh cannot sign or resubmit a transaction.

For Relay deposits, pending responses may include transient `progress` bound to the exact route, current funding action and original source hash. `SOURCE_CONFIRMED` requires independently verified funding: at least one canonical Base confirmation for Base sources, or finalized Solana funding for Solana sources. `DESTINATION_CONFIRMED`, when supplied, additionally verifies exact destination asset, recipient, minimum and signed-order attribution using the chain-specific payout adapter. It may display “Funds received · final confirmation pending” while status remains pending. COMPLETE requires twelve canonical Base confirmations and finalized Solana evidence in the applicable direction. Earlier progress cannot release the reservation or authorize a wallet action. Approval and proven-failure thresholds are unchanged.

POST `/v1/executions/:id/watch` accepts `{}` with the same app/origin and wallet token headers. It verifies ownership before opening an NDJSON response. Each frame has `apiVersion`, `requestId`, `appId`, `executionId`, a contiguous zero-based `sequence`, and `sentAtMs`. `START` opens the stream. `UPDATE` carries the same `execution`, `receiptStatus` and optional transient `progress` as refresh. `END` carries `reason`: `SETTLED` for COMPLETE/FAILED, `STATE_CHANGED` when another lifecycle state needs user action, or `TIMEOUT` when the bounded watch ends. `ERROR` carries a sanitized `error` object and is terminal. A clean EOF after END/ERROR is required; malformed frames cannot authorize recovery actions.

The server checks immediately, then sequentially with a 250 ms target cadence, flushing each verified observation directly. Source immutable-proof memoization is bounded to 32 entries per configured verifier and 60 seconds: the exact reviewed plan, action, transaction, receipt and block hash must match, with fresh chain/head/transaction reads and two canonical membership checks every time. No approval, failure or evidence from a different endpoint is reused. A discovered destination signature is only a hint: fresh independent destination proof remains mandatory. Progress is not persisted as final settlement or signing authority.

Progress is outside the durable execution record and review hash. It contains `routeId`, `actionId`, `sourceTransactionHash`, `stage`, `observedAtMs`, `sourceConfirmations`, and `requiredSourceConfirmations:12` for Base sources or `1` for finalized Solana source proof. The destination stage additionally contains `destination:{chainId,transactionHash,asset,recipient,amountRaw,commitment}`. Server and SDK validate this against the saved submission; unexpected fields, stale observations, incorrect identities and inadequate credit cannot appear as received funds. The controller exposes fresh evidence through `getProgress()` and discards it after fifteen seconds, on errors, or when the execution advances. It is not restored from browser storage.

The widget consumes authenticated push updates immediately. Only an unavailable stream endpoint (404/405/501) or connection loss with the original known submission permits bounded sequential read-only polling. Poll fallback uses a one-second target start cadence, accounting for request duration with at least 250 ms rest. Protocol, binding or ownership errors stop. Checks never overlap; a valid terminal reply arriving at the deadline is rendered. No wallet action is retried. Verification and transport latency prevent a universal one-second UI guarantee.

POST `/v1/executions/:id/cancel` accepts exactly `{reviewHash,revision}`. Untouched READY records may become CANCELLED. The exact Base USDC or generic-token approval-only prefix may also cancel from READY at nextAction 1, with no deposit claim or submission, after an independent canonical approval receipt recheck. Its submission remains in the journal. This does not revoke allowance. Claimed, submitted or uncertain funding actions cannot be cancelled to release a reservation.

Execution mutations do not accept Idempotency-Key and are not automatically retried. Quotas, body bounds, disconnect cancellation and operation deadlines apply. An aborted upstream check retains its transport slot until settled; no late check may publish a wallet action. A durable claim may remain recoverable if the HTTP response is lost. Store locks are never evicted automatically after an abrupt or uncertain writer exit.

New records include an append-only timeline (prepared/claimed/submission-reported/completed/failed observation timestamps). These are server lifecycle times, not exact wallet broadcast or chain-inclusion times. Terminal receipt evidence records chain, original transaction hash, canonical block number/hash, observation time, confirmation count, actual native fee when verified, and actual destination credit. Restart preserves this evidence. Only an explicit independently bound canonical reverted transaction proof permits terminal FAILED and releases the wallet reservation; generic unsuccessful verification remains RECOVERY_REQUIRED.

## Relay Base → Solana direct deposits

This profile requires reviewed Relay depository code/owner/allocator and Base solver pins, Base fee-oracle implementation pins and allowlisted Solana payout signers. Source is Base native ETH or a freshly verified standard ERC20; destination is native SOL or classic SPL on `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` when exact signed direct order and independent payout evidence support it. Source swaps, multicalls, Token-2022 and unsupported token behavior are rejected. Origin/app/source-wallet authentication, native gas policy, impact and slippage checks remain mandatory. Numeric caller limits apply when supplied; explicit null removes only the corresponding caller ceiling.

The locally reconstructed native deposit binds the exact provider order commitment. Relay review expiry is bounded to 60 seconds and shortened by the provider order deadline. Fresh preparation must finish within its separate 15-second pricing window. The source contract may not enforce UI expiry. Claimed or uncertain funding remains reserved after expiry; neither expiry nor an unavailable provider response permits another funding action.

`receipt` retains the independently confirmed Base transaction and has no cross-chain `destinationCredit`. `destinationReceipt` has `{chainId,transactionHash,blockNumberRaw,blockHash,observedAtMs,commitment:'finalized',destinationCredit:{asset,recipient,amountRaw},attribution:{provider:'relay',requestId,sourceTransactionHash}}`. Its transaction hash is the Solana signature; block number is the slot and block hash is base58. `requestId` is the raw Relay ID and matches `plan.quoteIds[0] === 'relay:'+requestId`; the source hash matches the original submission and source receipt. The destination verifier checks finalized canonical block membership, successful native/SPL payout, recipient balance increase at least the minimum and authorized solver transfers with a pinned signer's signed order-ID memo. This is a trusted solver declaration plus independent RPC payout evidence, not a bridge consensus certificate.

Source confirmation alone remains SUBMITTED. COMPLETE requires both source and destination proofs. A proven source revert permits FAILED and cannot carry destination delivery evidence; unknown/ambiguous delivery retains pending/recovery state. Both proofs and the journal's funding/order/payout replay claims survive restart and cannot be rewritten or erased. Status checks never ask either wallet to send again. The live Base USDC → Solana USDC execution recorded on 10 October 2026 (India) has exact finalized recipient-credit evidence; see [observed settlement timings](../../docs/validation/2026-10-10-settlement-latency.json). Historical receipts, quote/preflight checks and mocked tests do not validate unrelated routes.

Trusted configuration adds `executionPins.relay = {depository:{codeSha256,owner,allocator},solver,solanaSolverSigners:[publicKey]}` alongside existing `executionPins.base` pins. Each value must be independently reviewed; omitted pins keep the lane disabled. Operator-only `rpcEndpoints.solana` accepts a reviewed HTTPS endpoint list (default Solana mainnet-beta); callers cannot select RPCs. The Base-source Relay review cap is 60 seconds for native ETH and 90 seconds for ERC20 input; Solana-source reviews are capped at 60 seconds, with pricing capped at 15 seconds and provider expiry applied as an additional bound, within the lifecycle's 90-second maximum.

### Base ERC20 source variants

Canonical Base USDC keeps its pinned proxy checks and `relay-usdc-approve`/`relay-usdc-deposit` action IDs. Generic standard ERC20s use `relay-token-approve`/`relay-token-deposit` under `relay-base-direct-v1`, with observed code/decimals/proxy identity rechecked at claim and confirmation. Insufficient allowance creates a finite exact-amount approval to the pinned depository, followed by an exact explicit-amount deposit; sufficient allowance skips approval. Both carry zero ETH value. Each action binds its native reserve, whose sum is the reviewed plan total. Deposit simulation requires actual allowance at claim; no state override replaces it.

The intermediate confirmed approval returns READY even after expiry, at `nextAction: 1`, with no claimed action and the original approval retained. Expiry still blocks deposit claim; cancellation independently rechecks the sole approval receipt. The SDK returns to REVIEW and never executes from `resume()` or `watch()`. The browser may invoke the next exact approval/deposit action within the same active one-click consent scope, bound to unchanged wallet, inputs, immutable execution/review and expiry. Stop, errors, rejection, uncertainty, changed terms, reload or recovery end that continuation. Each required transaction still needs wallet confirmation. Only final deposit and independently attributed destination proof permit COMPLETE.

### Solana → Base native ETH

The `relay-solana-base-direct-v1` profile requires separately reviewed `executionPins.solanaRelay` containing the Base solver, Solana program address/owner/code digest and program-data address/digest, config address/owner/allocator, and vault. The source program is `99vQwtBwYtrqqD9YSXbdum3KBdxPAVxYTaQ3cfnJSrN2`. Native SOL uses the system sentinel `11111111111111111111111111111111`, 9 decimals; wrapped SOL remains a distinct classic SPL mint. Source amounts must fit uint64. The destination is native ETH on Base at an EOA. Base ERC20 output is blocked because an independently attributable payout recipe is not yet available.

The claim returns `relay-solana-deposit` with `payload.type: 'SOLANA_TRANSACTION'`, `transaction: {message,blockhash,lastValidBlockHeight,feePayer}` and Relay order metadata. `message` is the base58 reviewed legacy message, not a signed transaction. `relay.computeBudget` binds `{units:200000,microLamports:'decimal'}`; `nativeFeeCapRaw` binds its finite reserve. The engine locally constructs a legacy message with exactly two leading ComputeBudget instructions (200,000 units and the fresh reviewed micro-lamport unit price), followed by one exact Relay native/SPL deposit. It derives the config/vault and, for SPL, associated token accounts; binds sender, amount, order ID, recipient, minimum output, deadlines and refunds; checks token/program behavior and simulates the actual wallet message. The SDK repeats exact message reconstruction and checks the action digest and finite reviewed gas reserve. Phantom receives a base58 full unsigned transaction envelope: one empty 64-byte signature slot followed by the unchanged reviewed message. The wallet signs and submits once; the SDK never broadcasts or retries with a different wire format. Account checks run before and after the wallet request.

Completion requires the original Solana deposit at finalized commitment plus an independently attributed Base native-ETH payout with exact recipient/minimum, the signed order ID and at least twelve canonical Base confirmations. The Solana source receipt retains `confirmations: 1` and base58 signature/block hash. The Base destination receipt uses `commitment: 'canonical'` and `confirmations >= 12`, with EVM transaction/block hashes. Twelve Base confirmations are a canonical-depth policy, not Ethereum L1 finality. Provider success alone is insufficient.

## Optional caller fee and gas ceilings

Set `maxFeeBps: null` to omit the caller fee-percentage ceiling. Set `nativeFeeBudgets: [{chainId: "eip155:8453", maxAmountRaw: null}]` to request a fresh finite gas reserve without a preset native spending ceiling. Missing budget entries are invalid, and omitted fee limits retain their existing defaults. Numeric limits retain their existing enforcement. The example widget starts both optional fields blank and sends explicit nulls.

This does not waive complete fee evidence, slippage/minimum output, price impact, balance, transaction or contract checks. Known total costs may exceed the input value for tiny trades. Each immutable review still binds a finite gas reserve; Relay includes 25% headroom, and updated costs above a reviewed reserve require a fresh review. The wallet continues to approve transactions. Null and numeric policies are distinct in the review binding and durable recovery journal.

Expanded route probes are read-only simulations and offline fixtures. They are not live wallet submissions, measured trade RTT or evidence that all assets have liquidity. Historical completed Base USDC → Solana USDC evidence remains scoped to that route; broader execution still needs deployment review and user-authorized on-chain validation before production use.

## Broad provider-managed execution

Enable `executionPins.providerManaged.enabled` explicitly in trusted operator configuration. At startup the lightweight server reads official Relay `/chains` deployment/RPC metadata separately from RFQs, filters enabled EVM/Solana deployments, validates public HTTPS endpoints, and applies configured Base/Solana RPC overrides. If discovery fails, only the configured local recipes remain advertised. Library consumers may instead provide an independently reviewed `providerExecutionChains` snapshot to `createExecutionEngine`. API requests cannot supply RPCs, contracts, execution profiles or verification modes.

The `relay-provider-managed-v1` recipe requests exact-input official Relay `/quote/v2` transaction steps with explicit deposits, no permit/signature steps and no deposit-address flow. It binds the fresh RFQ digest, exact request, configured targets, supplied signed protocol order terms, finite exact approval, source gas/rent budget and expiry. Source DEX/multicall semantics remain a Relay construction trust assumption: these are not represented as locally reconstructed arbitrary DEX calls. Initial approval preparation never fabricates allowance to simulate funding; the actual funding transaction must pass simulation after the user has approved.

Plans persist `providerRoute:{provider,mode,requestId,quoteHash,sourceVm,destinationVm,sourceConfirmations,destinationConfirmations}`. Claimed actions use `PROVIDER_REVIEWED_TRANSACTION` version 1, with `rfq`, `spending`, exact `transaction`, immutable `bindings` and bounded validation evidence. EVM supports type 0 and 2; Solana carries a full unsigned legacy/v0 wire, fresh blockhash and resolved address lookup tables. The SDK verifies this envelope and the reviewed payload digest before handing it to the connected source wallet. A single Swap click can continue from exact approval to funding; each necessary wallet confirmation remains under user control.

Settlement verifies the original transaction body, canonical block membership and actual fees. Provider status associates the payout with the request and original funding hash; recipient credit is independently checked from the destination transaction. This distinct attribution is persisted as `basis: "PROVIDER_STATUS_AND_CHAIN_CREDIT"`. Final settlement requires twelve source/destination EVM confirmations where applicable and finalized Solana evidence. EVM native payouts require a direct value transfer or supported bounded canonical call trace. Provider success without matching credit cannot complete a trade.

Same-chain solver routes may use separate funding and payout transactions; only explicitly provider-managed plans permit a same-chain `destinationReceipt`. Atomic same-chain routes instead carry credit in the original receipt. Funding, order and payout replay protections and unknown-submission recovery remain active. Confirmed credit can be pushed to the UI before the final depth policy finishes; this is display evidence, never permission to resend or release an uncertain trade.

Gas accounting distinguishes independently modeled `STANDARD` (Ethereum/Arbitrum) and `OPSTACK` deployments from `PROVIDER_ESTIMATE` chains. All generic EVM reviews use at least the official full gas estimate as well as fresh execution gas, then add a finite reserve. Unknown-chain surcharge estimates are explicitly provider-trusted, not independently complete fee attestations. Claims recheck the immutable floor, actual known fees and native balance; confirmation rejects unaccounted fee components or a reserve overrun. An advertised chain is admission to fresh checks, not evidence that every chain-specific fee model or RPC trace has been validated live.
